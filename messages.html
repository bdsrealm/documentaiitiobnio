Chat is the easiest way to prove a client works: one packet, immediate feedback, and the server echoes it back to you.

Chapter three

Sending messages

Two routes produce visible text: the text packet, which is you talking, and command_request, which is you asking the server to run something — including /me, which is how an unattributed line gets into chat.

3.1 The text packet

One packet carries every kind of chat line Bedrock has. Its shape is needs_translation, a category, a type, a body that depends on the type, then the sender identity fields.

FieldTypeNotes
needs_translationboolfalse for raw chat; true only for translation keys.
categorymapper<u8> message_only 0 · authored 1 · parameters 2
typemapper<u8> raw 0 · chat 1 · translation 2 · popup 3 · jukebox_popup 4 · tip 5 · system 6 · whisper 7 · announcement 8 · json_whisper 9 · json 10 · json_announcement 11
bodyswitch on type chat/whisper/announcement take source_name + message; raw/tip/system/json* take message only; translation/popup take message + a string[]varint of parameters.
xuidstringThe sender's Xbox id; empty works, but clients send it.
platform_chat_idstringEmpty for normal chat.
filtered_messagestringPresent even when empty; the client always writes it.

The full field tree, including the switch cases, is on the reference page for text. The packet page is generated; this section explains which values you actually want.

3.2 A plain chat line

say in the console reaches the engine's say(), which writes a single text packet of type chat. Note that source_name is filled in but the server is free to replace it with your gamertag.

src/engine/bedrockx.js — say() 
say (message) {
  this.client.write('text', {
    needs_translation: false,
    category: 'authored',
    type: 'chat',
    source_name: this.bot.profile?.name || 'bot',
    message,
    xuid: this.bot.profile?.xuid || '',
    platform_chat_id: '',
    has_filtered_message: false,
    filtered_message: ''
  })
}

If your encoder rejects the call, the error is printed by connection.js rather than thrown at the caller — check the console, not a try/catch around the write.

3.3 /me, and why it looks different

/me is not text — it is a command. Asking the server to run it produces a chat line with no sender name attached, and the realm decides what to put there. The origin object is what it decides from:

origin.typeChat showsTypical use
playeryour gamertag, normal command attributioncommands that should look like the account ran them
automationplayer* External <text> — no nametag, no xuid/me floods, display text
 
// what engine.externalCommandRandom() writes, once per send
client.write('command_request', {
  command: '/me ' + message,
  origin: {
    type: 'automationplayer',
    uuid: randomUUID(),        // fresh per send
    request_id: randomUUID(),  // fresh per send
    player_entity_id: this.runtimeId ?? 0n
  },
  internal: false,             // true keeps it server-side, no chat line
  version: 'latest'
})

internal: true is the difference between "the server ran this quietly" and "everyone saw it". Every flood in this project sends false, because the point is the visible line.

3.4 Reading command output

The server answers with command_output. It echoes the origin.request_id you sent, which is how you match a reply to a request when several are in flight: 

const requestId = Math.floor(Math.random() * 1e9).toString()

client.on('command_output', (packet) => {
  if (packet.origin?.request_id !== requestId) return   // someone else's answer
  // packet.output[]  → [{ message_id, parameters[] }]
  // packet.has_data  → true when the command returned free text
})

client.write('command_request', {
  command: '/list',
  origin: { type: 'player', uuid: randomUUID(), request_id: requestId, player_entity_id: 0n },
  internal: false,
  version: 'latest'
})

Some commands legitimately return nothing (/say is the usual example). The engine treats a 10-second silence as "(no output — command was sent)" rather than an error.

3.5 Message loops

Three commands send repeatedly, and each exists because it behaves differently on the receiving end:

CommandPacketCadenceLine
spam [realm] <msg> on command_request, automation origin 1 per 50 ms, starting 5–8 s after the join, never before spawned /me <msg> | §…signature - §0<6-char code>
break <realm> <secs> on command_request 1 per 25 ms for the given duration external /me wall
admessage <realm> <secs> on command_request 1 per 25 ms plain text, no § codes at all
lag <realm> <player> on command_request fast loop /tell <player> … — a whisper, not public chat
mafter [realm] [msg] on command_request on incoming chat auto-reply, once per trigger

spam is the one with the most deliberate behaviour, so it is worth reading in full: it refuses to send before spawn, waits a random 5–8 seconds after the join, and rebuilds the origin uuid and request id for every single send. That last part is not cosmetic — identical origins are the easiest thing for a server to collapse into one action. 

// the shape of one spam tick
this.engine.externalCommandRandom(
  `/me ${base} | §4§o§l<signature>§r - §0<code>`
)

<code> is 6 characters of [A-Za-z0-9], regenerated per send, so consecutive lines are never byte-identical. The signature itself is styled with § formatting codes only — the server does not care, but the client renders them.

3.6 What comes back

Inbound text packets land as an event named after the packet, and the adapter sorts them by type before anything reaches the console:

Incoming typeHandling
chat with a source_nameprinted as <name> message
chat with an empty sourceprinted as-is — this is how a /me line arrives (* External …)
whisper, json_whisperprinted with a [whisper] prefix
raw, system, announcement, json, json_announcementprinted as server text
popup, tip, translation, jukebox_popupdropped

Both directions strip § codes before printing, and translation-style payloads are decoded first — otherwise the console fills up with raw rawtext JSON.

3.7 Gotchas

  • One write is one batch. Sending 60 messages does not send one batch of 60 — it sends 60 batches. At 25 ms cadence that is 40 packets/second of pure overhead; it works, but it is why message loops cost more than they look like they should.
  • Chat is rate-limited server-side. Different realms use different thresholds and some anti-bot addons kick on the first burst. The 5–8 second arming delay exists because sending before the join finishes simply gets dropped.
  • Length limits are enforced by the server, not the encoder. A 400-character "message" serialises fine and gets rejected.
  • Commands need permission. /me is allowed to everyone; anything else may silently fail or come back as an error line in command_output.
  • player_entity_id should be your runtime id, which only exists after start_game. Sending 0n works on most servers, but it is a tell.

These loops are spam by design. On realms you do not own, that is a ban waiting to happen, and it is against the terms of service in most contexts. The code is documented so the protocol is understood, not as an invitation.
