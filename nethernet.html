NetherNet

The transport Bedrock uses instead of RakNet for realms and cross-network LAN play: a UDP discovery/beacon layer on port 7551, a Microsoft-hosted signalling WebSocket, and a WebRTC data-channel pair carrying the normal Bedrock batch. Everything below is what src/engine/bedrockx-lib/nethernet/ implements.

Transport modes

NETHERNET

UDP discovery + WebRTC, signalling over wss://signal.franchise.minecraft-services.net/ws/v1.0/signaling/<id> with the compact {Type, To, Message} envelope.

Transport modes

NETHERNET_JSONRPC

Same WebRTC, different signalling API: …/ws/v1.0/messaging/connect with JSON-RPC 2.0 methods (Signaling_*). Used by newer realms endpoints.

Transport modes

DEFAULT

RakNet. 0xfe batch header, AES-GCM frames, native .node binding. See the engine page.

Layering

UDP 7551 broadcast WSS signalling (either one, for signalling only) discovery_request ─┐ discovery_response ─┼─► peer table │ discovery_message ─┘ sender_id → addr │ ▼ signal strings: CONNECTREQUEST / CONNECTRESPONSE / CANDIDATEADD │ ▼ WebRTC (ICE + DTLS) ├─ ReliableDataChannel ordered └─ UnreliableDataChannel unordered, maxRetransmits 0 │ ▼ segment framing: byte0 = segments remaining, 50 000 B chunks │ ▼ Bedrock batch: [compressor id][deflate] · no 0xfe · no AES

The important consequence: over NetherNet the Bedrock payload is not encrypted by the Bedrock layer and carries no 0xfe batch header — DTLS already provides both confidentiality and integrity. The compression byte survives.

1 · Discovery on UDP 7551

nethernet/src/client.js opens a udp4 socket, enables broadcast, and every 2 seconds sends a discovery_request to 255.255.255.255:7551. Any peer answers with a discovery_response whose data field is that peer's advertisement JSON; the client stores sender_id → {rinfo, params} so it can send unicast discovery_message packets back to a chosen peer.

Secure wrapper (both discovery packets and all their replies)

packet = HMAC-SHA256(body)      // 32 bytes, plaintext
       + AES-256-ECB(body)      // ciphertext

key    = SHA-256( LE64(0xdeadbeef) )   // static, same for every peer

That static key is what nethernet/src/crypto.js builds. It is obfuscation, not security — there is no key exchange and no per-session secret at this layer. Everything that actually needs to be secret is inside WebRTC/DTLS.

The three packets

id (lu16 mapper)NameFields
0discovery_request sender_id: lu64, reserved: bytes[8]
1discovery_response sender_id: lu64, reserved: bytes[8], data: string<lu32> (advertisement JSON)
2discovery_message sender_id: lu64, reserved: bytes[8], recipient_id: lu64, data: string<lu32> (signal string)

Packet framing inside the encrypted body is protodef ["encapsulated", { lengthType: "lu16" }]: a 2-byte little-endian length, then the mapper id as lu16, then the switch body. The full schema is 60 lines: src/engine/bedrockx-lib/nethernet/src/protocol.json.

sender_id is a 64-bit value. Over UDP it is the peer's NetherNet numeric id; over the signalling WebSocket the same ids appear as JSON, which is why json-bigint is used — a plain JSON.parse rounds anything above 253 and the routing silently targets the wrong peer.

2 · The signalling WebSocket

Legacy envelope (NETHERNET)

websocket/signal.js connects to wss://signal.franchise.minecraft-services.net/ws/v1.0/signaling/<serverNetherNetId> with these headers:

HeaderValue
AuthorizationBedrock services token from authflow.getMinecraftBedrockServicesToken({ version })
session-idthis client's random uint64 NetherNet id
request-idfresh v4 uuid per connect

Messages are JSON, all keys capitalised:

TypeDirectionMeaning
0 RequestPingboth Liveness. Client sends one every 2 s; if nothing arrives for 60 s it terminates the socket.
1 Signalboth { Type: 1, To: <peer id>, Message: "<signal string>" } in, and From identifies the sender on the way back.
2 Credentialsserver only Message is JSON containing TurnAuthServers. connect() waits up to 15 s for it.

Reconnect policy: close codes 1006, 1011, 4401 (and 0) retry up to 5 times, 15 s apart. Anything else emits error. Every reconnect re-fetches the Bedrock services token.

JSON-RPC envelope (NETHERNET_JSONRPC)

websocket/signal-jsonrpc.js connects to wss://signal.franchise.minecraft-services.net/ws/v1.0/messaging/connect and speaks JSON-RPC 2.0:

MethodPurpose
Signaling_TurnAuth_v1_0requested on open — TURN credentials come back as result.TurnAuthServers.
Signaling_SendClientMessage_v1_0 params: { toPlayerId, messageId, message }; message is a JSON-RPC string itself: Signaling_WebRtc_v1_0 with params.netherNetId and params.message (the signal string).
Signaling_ReceiveMessage_v1_0 incoming; the client acknowledges with result: null and then sends Signaling_DeliveryNotification_V1_0 back to the sender.
System_Ping_v1_0 / System_Pong_v1_0 ping every 60 s, pong echoed with the same id.

3 · The signal strings

Both signalling flavours carry the same text format (nethernet/src/signalling.js): 

<TYPE> <connectionId> <data…>

TYPE         CONNECTREQUEST | CONNECTRESPONSE | CANDIDATEADD | CONNECTERROR
connectionId this connection's random uint64 — answers and candidates echo it back
data         for CONNECTREQUEST / CONNECTRESPONSE: the whole SDP (spaces and newlines intact)
             for CANDIDATEADD: the ICE candidate string

Parsing splits on the first two spaces only, then re-joins the remainder — SDP is full of spaces and must survive untouched.

4 · WebRTC

The offer

  1. Peer connection — new RTCPeerConnection({ iceServers: credentials, bundlePolicy: 'max-bundle' }). iceServers is the TURN list the signalling server just handed over; without it a remote realm has no relay path and the data channel never opens.
    This is the fork's whole reason to exist: upstream v1.4.6 hardcodes iceServers: [] and therefore cannot join remote realms at all.
  2. Two data channels, created by the client — ReliableDataChannel { ordered: true } and UnreliableDataChannel { ordered: false, maxRetransmits: 0 }. Bedrock only ever sends on the reliable one; the unreliable channel exists because the vanilla client creates it.
  3. SDP munging — replace the o= line with o=- <localNetworkId> 2 IN IP4 127.0.0.1 so the server sees the NetherNet id instead of a random session id.
  4. Identity assertion — take a=fingerprint:sha-256 <HEX>, sign a JSON document with the client's P-384 key (ES384 JWS), then append a=identity:<base64>. Details below.
  5. Send — CONNECTREQUEST <connectionId> <sdp> to the server's NetherNet id.

The identity assertion

// 1. signed payload
JSON: { "fingerprint": [ { "algorithm": "sha-256", "digest": "<sdp fingerprint hex>" } ] }

// 2. compact JWS, ES384, key = client P-384 private key
jws = base64url(header).base64url(payload).base64url(signature)
      header = { alg: "ES384" }

// 3. payload is dropped on purpose
fingerprints = `${jws.split('.')[0]}..${jws.split('.')[2]}`

// 4. wrapped with the Xbox identity provider
assertion = JSON.stringify({ fingerprints, token: <bedrock services token> })
a=identity:base64(JSON.stringify({
  assertion,
  idp: {
    domain: "https://authorization.franchise.minecraft-services.net/",
    protocol: "default"
  }
}))

The token embedded here is the same mcToken used as the signalling Authorization header. The server validates that the signed SDP fingerprint matches the certificate it actually sees in the DTLS handshake — which is what stops anyone from impersonating a peer's media identity.

ICE

Every local candidate is sent as CANDIDATEADD, except host-loopback and TCP candidates, which this client drops (tcp, ::1, 127.0.0.1). Incoming candidates are parsed back into field-by-field RTCIceCandidate objects (foundation, component, protocol, priority, address, port, type, raddr/rport, ufrag).

Candidate id rewrite. A CANDIDATEADD that arrives with the server's NetherNet id in networkId is rewritten to this connection's local id before being applied. Skip that and multi-connection bots misroute each other's candidates.

Answer handling (the multi-client patch)

The signalling service fans a message out to every socket authenticated as the same player. With several connections at once (a bot firing three joins per loop), each peer therefore receives the other connections' answers first. Applying a foreign answer moves the peer connection to stable, after which its own answer is rejected ("answer in stable state") and only one of N connections ever works. 

// nethernet/src/client.js — LOCAL PATCH, not upstream
if (signal.connectionId != null &&
    String(signal.connectionId) !== String(this.connectionId)) return

switch (this.rtcConnection.signalingState) {
  case 'stable': return   // already answered
  case 'closed': return   // nothing to do
}

5 · Data-channel framing

A Bedrock batch can exceed what one SCTP message should carry, so nethernet/src/connection.js splits it: 

MAX_MESSAGE_SIZE = 50 000 bytes        // SCTP's hard ceiling is 262 143

segments = ceil(len / 50000)
message[i] = [ (segments - 1 - i) , chunk_i ]   // byte 0 = segments still to come

receiver: accumulate; when byte0 == 0 emit('encapsulated', whole buffer)
          a mismatch against promisedSegments throws "Invalid promised segments"

Sends made before the reliable channel reports open are queued and flushed on onopen; sending on a closing/closed channel throws Reliable channel is not open.
