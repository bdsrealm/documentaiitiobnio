The client does not move the player. It reports what the player did, twenty times a second, and the server decides whether that was true.

Chapter four

Movement

Bedrock movement is client-authoritative with server correction: you send your position in player_auth_input, the server answers with move_player to agree or drag you back, and everything else — jumping, sneaking, riding — is a flag in the same packet.

This bot does not move today. It listens to move_player for logging (teleports, chunks, nocom, botdet, blindad/cblind) and for the anticrash position guard, but nothing sends player_auth_input. This chapter is what it would take to add that.

4.1 The model

client, 20× per second server player_auth_input position, move_vector, yaw, tick ──────────────────────────────▶ validate / simulate move_player mode normal | reset | rotation | teleport ◀────────────────────────────── reject → snap back set_entity_motion velocity (knockback, water, pistons) ◀──────────────────────────────

There is no "walk to x" packet. The client integrates its own movement and tells the server where it ended up; the server compares that against its own simulation of you and either accepts it or sends a correction. Two consequences shape every implementation:

  • You must run a tick loop. Send at roughly 20 Hz, not on demand — the server expects a heartbeat and some anti-cheats measure its regularity.
  • You must accept corrections. If you keep sending the position you wanted instead of the one the server gave back, you will be rubber-banded forever and eventually kicked.

4.2 player_auth_input

FieldTypeWhat to put there
pitch, yawlf32 Degrees. Pitch −90 looks straight up, +90 straight down. Yaw 0 faces +Z, 90 faces −X.

Full switch cases and nested option types: the player_auth_input page. Field order matters — protodef writes them in schema order, and it is not the order a wiki lists them in.

4.3 What the server sends back

move_player.mode
normal accepted · reset health/respawn reset · rotation yaw/pitch only · teleport forced position.
move_player.on_ground
Authoritative ground state. Copy it; do not invent it.
move_player.teleport.cause
unknown · projectile · chorus_fruit · command · behavior.
set_entity_motion
Velocity the server applied to you (knockback, water current, pistons). Ignore it and your next position will be wrong.
tick_sync
request_time / response_time, both li64. Servers send it to measure the tick the client is on; a client that never answers drifts.

4.4 A minimal walker

This is enough to walk in a straight line and stay corrected. It assumes you have client (the bedrockx client) and a runtime id from start_game.

movement.js — 20 Hz tick loop 
const TICK_MS = 50
const WALK = 4.317 / 20          // blocks per tick, walking speed
let ticks = 0n
let pos = { x: 0, y: 64, z: 0 }  // replace with the spawn position
let yaw = 0, pitch = 0
let onGround = true
let jumping = false

// adopt the server's position whenever it disagrees
client.on('move_player', (p) => {
  if (p.runtime_id !== client.runtimeId) return       // someone else moving
  if (p.mode === 'teleport' || p.mode === 'reset') {
    pos = { x: p.position.x, y: p.position.y, z: p.position.z }
    onGround = p.on_ground
    return
  }
  pos = { x: p.position.x, y: p.position.y, z: p.position.z }
  onGround = p.on_ground
  if (p.mode === 'rotation') { yaw = p.yaw; pitch = p.pitch }
})

client.on('set_entity_motion', (p) => {
  if (p.runtime_entity_id !== client.runtimeId) return
  // server applied velocity — let the correction arrive, don't fight it
  pos = { x: pos.x + p.velocity.x, y: pos.y + p.velocity.y, z: pos.z + p.velocity.z }
})

function step (dx, dz) {
  const from = { ...pos }
  pos = { x: pos.x + dx, y: pos.y + (jumping ? 0.42 : 0), z: pos.z + dz }

  client.write('player_auth_input', {
    pitch,
    yaw,
    position: pos,
    move_vector: { x: dx, z: dz },
    head_yaw: yaw,
    input_data: jumping ? ['jumping'] : [],
    input_mode: 'mouse',
    play_mode: 'normal',
    interaction_model: 'crosshair',
    interact_rotation: { x: 0, z: 0 },
    tick: ticks++,
    delta: { x: pos.x - from.x, y: pos.y - from.y, z: pos.z - from.z },
    transaction: undefined,
    item_stack_request: undefined,
    block_action: [],
    vehicle_rotation: undefined,
    predicted_vehicle: undefined,
    analogue_move_vector: { x: dx, z: dz },
    camera_orientation: { x: 0, y: 0, z: 0 },
    raw_move_vector: { x: dx, z: dz }
  })
}

// yaw 0 = +Z, 90 = -X
function forward (yawDeg) {
  const r = yawDeg * Math.PI / 180
  return { x: -Math.sin(r), z: Math.cos(r) }
}

setInterval(() => {
  if (!client.runtimeId) return
  const f = forward(yaw)
  step(f.x * WALK, f.z * WALK)
}, TICK_MS)

Verify the yaw convention against the server, not against this page. Send one tick, read the move_player that comes back, and check that the position moved the way you expected. If it goes sideways, your sign is flipped — fix it before building anything on top.

4.5 Turning, looking, jumping

  • Turn by changing yaw and sending the same position — the server replies with mode: rotation when it accepts a pure rotation.
  • Jump by including 'jumping' in input_data for one tick, and giving position.y a small rise. onGround from the server decides whether the jump is possible.
  • Sneak with 'sneaking'; sprint is a modifier on your own speed, not a separate packet.
  • Swim / fly add ascend/descend and depend on the player's abilities — the server clamps movement it did not grant.

4.6 Other ways to move

ApproachHowReality check
Teleport commandcommand_request with /tp Needs operator or a permission-granting addon. Otherwise it just fails.
Vehicleinteract on a boat/minecart, then vehicle_rotation The server drives the position; you only steer.
KnockbackTake a hit, follow set_entity_motion Unreliable and obvious; not a movement system.
Fake position onlySend player_auth_input without a matching tick loop Rubber-band. The server simulates you; it will not accept teleporting without cause.

4.7 Risks and tells

  1. Never moving is a signal. Some anti-bot addons kick clients that spawn and stay still forever; a slow patrol loop is what makes a bot look alive.
  2. Tick jitter is a signal. setInterval(50) drifts under load. Track the wall clock and send early when behind, but never send two ticks in one millisecond.
  3. Impossible movement is a signal. Do not scale speed above vanilla, do not fly without abilities, and do not skip collisions — the server checks the same things.
  4. Position sanity is enforced locally too. This project's anticrash guard drops any inbound packet whose position is NaN or absurd, so a bug in your own position math shows up as missing updates rather than a crash.
