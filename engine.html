bedrockx engine

The patched fork in src/engine/bedrockx-lib/: a from-scratch Bedrock client (protodef + RakNet/WebRTC) wrapped by src/engine/bedrockx.js, the adapter the bot actually calls. Everything on this page is what those files do, in order.

Why the start_game acks matter

Realms drop a client roughly 8 seconds after start_game unless it confirms it reached the world. bedrockx.js sends serverbound_loading_screen (type: 2), request_chunk_radius and set_local_player_as_initialized — the runtime entity id comes from start_game.runtime_entity_id. Without that trio, spawn never completes and the connect promise only ends at the 60 s timeout.

4 · Encryption (DEFAULT transport only)

secret  = SHA-256( Buffer.from(payload.salt, 'base64')
                 ‖ ECDH(clientPrivate, serverPublicFromHeader.x5u) )

key     = secret[0..32]        // AES-256
iv      = secret[0..12]        // taken from the same bytes
cipher  = aes-256-gcm, stream mode — updated per batch

frame   = [0x00][deflateRaw(batch)]     // or [0xff][batch] when under threshold
checksum= SHA-256( LE64(counter) ‖ frame ‖ secret )[0..8]
wire    = AES(frame ‖ checksum)         // counter increments per batch, per direction

The GCM tag is not used; the 8-byte SHA-256 checksum is the integrity check. Receiving verifies it against a separate receiveCounter and disconnects with disconnectionScreen.badPacket on mismatch.

Counters are state, not per-packet. One dropped or duplicated batch desynchronises sendCounter / receiveCounter permanently — every later frame fails its checksum. Any code path that bypasses sendMCPE() must not touch the cipher.

Over NetherNet both directions skip this entirely: disableEncryption = true, and the framer writes no compression byte until compressionReady. DTLS secures the channel.

5 · Framing and compression

batch    = [0xfe]                      // DEFAULT only
         + concat( varint(len) + packet … )
         + compression?
             compressor byte 0x00 (deflate) when len > threshold (512)
             compressor byte 0xff (none)   otherwise, if features.compressorInHeader
body     = deflateRaw(batch) when compressing

one write() = one batch = one sendReliable(..., immediate)
                 RakNet: RELIABLE_ORDERED, IMMEDIATE priority
             NetherNet: ReliableDataChannel
There is no write coalescing. Each write() serialises, frames, compresses and hands one buffer to the transport immediately. That is exactly what makes packet floods possible (setInterval(…, 0) really does produce thousands of sends per second) — and it is also why a flood needs a pre-built payload instead of re-serialising a million-element array on every tick.

6 · Serializer and custom types

transforms/serializer.js compiles protocol.json plus datatypes/compiler-minecraft.js with ProtoDefCompiler and exposes the root type mcpe_packet: 

const { createSerializer, createDeserializer } = require('./transforms/serializer')

const ser = createSerializer()
const buf = ser.createPacketBuffer({ name: 'login', params: { … } })  // id + body

client.write('login', { … })      // same thing, then frame + send
client.on('text', (params) => …)  // deserialized params of one packet
TypeEncoding
uuid16 raw bytes (uuid-1345). Not a string on the wire.
nbtLittle-endian NBT with varint lengths (network NBT).
lnbtLittle-endian NBT with fixed widths; an end tag costs exactly 1 byte.
entityMetadataLoopRepeated key/value entries until endVal.
ipAddressFour raw bytes, dotted on the wire as text only in logs.
endOfArrayReads to EOF — no count prefix at all.
mapperNumeric id ↔ name; either side accepted when writing.
ShieldItemID is a compile-time variable. Some item stacks encode differently when they are a shield, and the runtime id is only known after item_registry arrives. client.js (and the relay) call proto.setVariable('ShieldItemID', state.runtime_id) for minecraft:shield. Send item stacks before that point and they encode wrong.

10 · Server and relay

server.js / serverPlayer.js implement a listener that accepts Bedrock clients; relay.js extends it into a proxy: on a player's login it opens an upstream Client to the real destination, then forwards packets both ways.

  • client_cache_status { enabled: false } is sent upstream so the backend does not expect a client cache.
  • level_chunk packets that arrive before start_game are buffered and flushed after it.
  • item_registry is sniffed to set ShieldItemID on both serializer and deserializer.
  • update_player_game_type addressed to the relayed player is rewritten to set_player_game_type.
  • play_status: login_success from upstream is swallowed — the local client already handled its own login.
  • Handlers can des.canceled = true / des.modified = true to drop or re-serialise a packet.

11 · Authentication

Tokens come from prismarine-auth's sisu flow. The fork prefers its own nested copy (node_modules/bedrockx/node_modules/prismarine-auth) and falls back to the project's. Device spoofing (devicewoof) sets both the auth title (default Titles.MinecraftIOS, deviceType: 'iOS') and the DeviceOS in the login payload — the server compares them, so changing one alone gets the login rejected.

getMinecraftBedrockServicesToken()
the mcToken used as the signalling Authorization header and inside the WebRTC identity assertion.
token
raw Xbox token placed in login.tokens.identity.
tokenData.mid
used to build SkinId / PlayFab ids in the login JWT.
clientX509
P-384 public key, base64 DER SPKI, published as the JWT x5u header.

12 · Debugging checklist

  1. Nothing on the wire at all — check spawned / loginAccepted; most write helpers throw before that, and connection.write() swallows serializer errors with a console.log.
  2. Kicked right after join — the start_game acks did not land, or the device/auth-title pair mismatches.
  3. Checksum mismatch — counter drift on the DEFAULT transport; reconnect, do not retry.
  4. Parse error loop — a schema mismatch: the server sent a packet id whose body this protocol.json cannot read. isParseError() downgrades these to debug logs.
  5. Realm joins but the world never loads — resource pack reply or chunk radius never sent; both are automatic in createClient().
  6. Spam/flood sends nothing — the transport is up but the bot is not spawned; early floods must use the loginAccepted hook, not spawned.
Payloads for floods live in src/bot.js (PACKET_FLOOD_SPECS / packetFloodSend). Browse the arrays they use on the packets page — every field name there is exactly what this serializer expects.
