Two tokens, two purposes: an Xbox token to prove who you are, and a Bedrock session token that binds that identity to the key you will sign the handshake with.

Chapter five

Authentication

Signing in is three separate exchanges: Microsoft/Xbox gives you a token, Bedrock's authorization service turns it into a session bound to your P-384 key, and the login packet hands both to the realm — which is what stops anyone replaying a token without the key.

5.1 The whole flow

console prismarine-auth franchise.minecraft-services.net Authflow(username, profilesFolder, { flow:'sisu', authTitle }) │ ▼ device code printed ──▶ microsoft.com/link ──▶ token cache in ./profiles │ ▼ getMinecraftBedrockServicesToken({ version }) │ → mcToken (Bedrock services JWT) ▼ POST /api/v1.0/multiplayer/session/start Authorization: mcToken body: { publicKey: <P-384 SPKI, base64> } │ ▼ signedToken (JWT) → tokenData = payload, token = signedToken │ ▼ login packet: tokens.identity = { AuthenticationType: 0, Certificate: {chain:[]}, Token: signedToken } tokens.client = JWT signed with the same P-384 key (header.x5u)

5.2 Device-code sign-in

The default flow is sisu — the device-code flow Xbox uses for consoles and CLI tools. A code is printed, you enter it at microsoft.com/link, and the resulting tokens are cached as JSON under the profiles folder so subsequent runs are silent. 

const { Authflow, Titles } = require('prismarine-auth')

const flow = new Authflow(
  'bot',                              // profile name — the cache file is per name
  './profiles',
  { flow: 'sisu', authTitle: Titles.MinecraftIOS, deviceType: 'iOS' },
  (code) => console.log(code.message)  // "To sign in, use a web browser to open ..."
)

authTitle decides which game's token you get, and it has to agree with the DeviceOS you put in the login payload. That is the whole reason the device table exists — see §5.5.

5.3 The Bedrock session

mcToken alone is not enough to play. The client asks Bedrock's authorization service to open a multiplayer session, sending its public key:

src/engine/bedrockx-lib/client/auth.js 
POST https://authorization.franchise.minecraft-services.net/api/v1.0/multiplayer/session/start

authorization: <mcToken>
content-type:  application/json
user-agent:    libhttpclient/1.0.0.0

{ "publicKey": "<base64 DER SPKI, secp384r1>" }

The reply carries result.signedToken. Decoding its payload gives the account identifiers the login JWT needs (mid, used to build the PlayFab id and SkinId), and the token itself goes into the login packet verbatim. A PlayerBanned result is surfaced as a forbidden error before any join is attempted.

5.4 The login packet

Two JWTs go in login.tokens, and they are not the same kind of thing:

FieldContentsSigned by
tokens.identity JSON.stringify({ AuthenticationType: 0, Certificate: JSON.stringify({ chain: [] }), Token: signedToken }) Microsoft — the realm verifies it
tokens.client The skin/device payload, as a JWT whose header carries x5u: <public key> You, with the P-384 private key generated at startup (ES384)

The client payload is the big one — skin geometry, resource patch, device model, input modes, GUI scale, memory tier. Defaults come from a bundled skin JSON and are then overridden by options.skinData, so a device spoof only has to supply the fields it cares about. 

payload = {
  GameVersion: '1.26.60',
  PersonaSkin: true,
  DeviceOS: 1, DeviceModel: 'SAMSUNG SM-G955U',
  CurrentInputMode: 2, DefaultInputMode: 2,
  SelfSignedId: uuidv3(), DeviceId: uuidv4(),
  LanguageCode: 'en_US', MaxViewDistance: 12, MemoryTier: 4,
  ...steve,              // skin from skins/steve.json
  ...options.skinData    // device spoof overrides
}

JWT.sign(payload, privateKey, { algorithm: 'ES384', header: { x5u: publicKeyBase64 } })

DeviceOS and authTitle are checked against each other. Claim DeviceOS: 2 (iOS) with a token minted for the Java title and the login is rejected — usually as a generic kick, which is why this is such an annoying bug to diagnose.

5.5 Device spoofing

devicewoof sets one entry from a fixed table. Each entry bundles the three things that must agree: protocol DeviceOS id, a model string, and the MSA title/device type used to fetch the token.

KeyDeviceOSTitle / device type
undefined0MinecraftJava / Windows
android1MinecraftAndroid / Android (default model SAMSUNG SM-G955U)
ios2MinecraftIOS / iOS (iPhone14,3)
osx3MinecraftJava / macOS
win10 · win327 · 8MinecraftJava / Windows
playstation11MinecraftPlaystation / PlayStation
nintendoswitch12MinecraftNintendoSwitch / Nintendo
xbox13MinecraftJava / Xbox
linux15MinecraftJava / Linux
 
devicewoof list        # all 16 entries with os ids and titles
devicewoof ios         # spoof iOS for the next join
devicewoof off         # clear, back to client defaults
account                # confirm what the join will actually present

The spoof is stored in config.json as "device", so it survives restarts. Apply it with reconnect — the token is minted at connect time.

5.6 Where tokens live

PathContents
./profiles/*.jsonLive prismarine-auth cache: MSA refresh token, Xbox tokens, Bedrock services token. One profile name per account.
./accounts/<name>/A saved copy of the whole profiles folder plus meta.json (gamertag, xuid, uuid, savedAt).
config.jsonAccount profile name, realm, engine, device spoof. No tokens.
 
account save                  # save the current login under its gamertag
account save alt              # or a name you pick
switch list                   # what is saved
switch alt                    # restore it and relaunch the bot
switch delete alt

switch copies the saved files into ./profiles, rewrites the account name in config.json, and relaunches the bot the same way run.bat does — non-elevated, in a new console window.

Everything under profiles/ and accounts/ is credential material. Do not commit it, do not paste it into a chat, and do not share a profiles folder between two running clients of the same account — they will fight over the token cache.

5.7 From account to address

Authentication and realm resolution are separate. The Realms API lists the account's worlds, accepts pending invites, and — most importantly — answers GET /worlds/{id}/join with both the connection details and the transport: 

{ "host": "e27d6dd2-…", "port": 19132, "networkProtocol": "NETHERNET" }

DEFAULT means a RakNet address (host:port); NETHERNET means that "host" is a NetherNet id to signal, not an IP. Everything after this point is the transport chapter.
